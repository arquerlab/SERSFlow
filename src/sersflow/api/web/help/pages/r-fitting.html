Peak fitting

The Peak Fitting step describes a model (a sum of peaks and optionally a background), fits it to each spectrum and writes the fitted parameters as feature columns.

What the step does

  • Engines: vibrational pipelines use SciPy bounded curve_fit; XPS pipelines use lmfit, which adds the Vary checkboxes, parameter links, active backgrounds and the Fermi edge.
  • It replaces the spectrum with the fitted curve. Any later step (Normalization, Integration…) sees the model, not the data. Points outside the fit window keep their original values.
  • The exported columns come from re-fitting the step's input, so they are independent of later steps.
  • If a fit fails, the spectrum passes through unchanged, but the failure is recorded: its fit columns are empty, gof_success is 0 and the run shows a warning (see Failed fits).
  • XPS fits are Poisson-weighted by default (see Weighting). The weighting used is shown at the top of the Peak Fitting step and in every fit plot title.

Initial guesses

  • Centre (pos) starts at 1000 in every pipeline, including XPS. Always set it near the real peak (or use a recipe).
  • Amplitude is the peak height. The Auto checkbox lets SpecFlow estimate it. Typing 0 or a negative number switches Auto back on.
  • Widths (FWHM): the vibrational engine has no safety limits, so set an upper bound; XPS applies sensible limits automatically.
  • With Vary off in a vibrational fit, the value is fixed.

GL(m) product versus SGL(m) sum

CasaXPS has two Gaussian–Lorentzian line shapes (CasaXPS Cookbook 2026, p. 67). With u = (x − pos)/F and p = m/100:

  • GL(m), product: exp(−(1 − p)·4 ln2·u²) / (1 + 4p·u²). This is what CasaXPS writes as GL(30) and what the Biesinger recipes were fitted with. SpecFlow component gl.
  • SGL(m), sum: p·L + (1 − p)·G with a shared FWHM. SpecFlow component sgl.
  • GL(m,n): GL(m) convolved with a Gaussian of FWHM n (fwhm_g, in eV). SpecFlow component gl_gauss.

For the product form, CasaXPS's F is not the full width at half maximum: the true FWHM is slightly smaller (about 0.96·F at m = 30). SpecFlow's fwhm is always the true FWHM, the value Biesinger tabulates and CasaXPS shows in its component table. SpecFlow derives F internally. Areas use the closed form ∫ = (π/√b)·erfcx(√(a/b)) with a = 4 ln2 (1 − p), b = 4p, so area ratio links work for gl as well.

Pipeline schema v2. Before v2, SpecFlow's gl was the sum form. On the first server start with v2, every stored pipeline, session and run snapshot is rewritten gl → sgl and a_gl → a_sgl, so old results reproduce exactly. Their pipeline hash changes; runs keep the hash they were made with. Pipeline packages exported as sersflow.pipeline.v1 are converted the same way on import. A new gl anywhere (UI, MCP, v2 packages) means the product form. Re-applying a recipe gives the product form.

Links (XPS only)

In the Link column choose a target “<peak>.<parameter>” and a relation: equal, scale (× factor) or offset (+ value). The linked parameter then follows its target and is no longer free. Its own bounds are not applied (they are greyed out): it follows the relation exactly, as in CasaXPS. The link field is marked with the plot colour of the peak it follows (grey when it follows several). Typical use for a doublet: FWHM equal to the main component, position offset by the spin–orbit splitting. A scale link on amplitude fixes a height ratio. For an area ratio (e.g. a satellite locked to its main peak by the literature area ratio) use the area ratio relation on an amplitude: the dependent area is ratio × the driver area whatever FWHM and line shape each peak ends up with. It works for every peak line shape with a finite area (GL, SGL, GL(m,n), Voigt, LA, LF, A-GL, APV, …; not DS/GDS, whose tail has no finite area). Recipes lock satellites and spin–orbit doublets this way by default. To build a doublet in one step use Spin-orbit partner… under a peak (see XPS → Spin–orbit doublets).

Expressions

Choose Expression… in the Link column to write any relation between parameters, as CasaXPS constraints do. Reference parameters as {peak.param}:

ExampleMeaning
{A.pos} + 0.5*({B.pos} - {A.pos})C halfway between A and B (on C.pos)
{A.fwhm}*1.220 % broader than A
0.3*({A.area} + {B.area}) with defines: areaC's area is 30 % of A + B (on C.amp; the amplitude is solved through C's line shape)
sqrt({A.fwhm}**2 + {B.fwhm}**2)widths added in quadrature
  • {A.area} is the peak area. Use defines: area on an amplitude to give a peak's area instead of its height.
  • Allowed: numbers, + - * / **, parentheses and abs sqrt exp log min max. Nothing else is evaluated.
  • Peak names may contain symbols ({Co3+.pos}, {2p3/2_sat.area}). Renaming a peak updates the expressions that mention it.
  • Problems are shown above the component list as you type, and the fit refuses to run with them: unknown peaks or parameters, a parameter defined by two links, a parameter depending on itself, and loops such as C.pos → B.pos → C.pos.
  • API: POST /fitting/validate-links; MCP: post_fitting_validate_links. In pipeline JSON: {"source_component_id": "C", "source_key": "pos", "mode": "expr", "expr": "{A.pos} + 0.5*({B.pos} - {A.pos})"}.

Previewing a fit

There is no interactive fitting. Set View → After: fitting (or Final if the fit is the last step). SpecFlow fits each spectrum of the subset once and draws data, total fit, individual components and a residual panel with diagnostics. It refreshes when you change the view or subset, or press Run preview plot (subset), not after every parameter edit.

Start with one peak on one spectrum, check the residual, then add peaks one at a time. Narrow the fit window rather than adding background peaks.

Fitting results

Per component: fit_[region_]<peak>_<param>, …_area and …_area_pct (all peak types except DS and GDS), each with a 1σ error column …_stderr (see Uncertainties). Per fit: fit_[region_]gof_<rmse|r2|r2_adj|aic|bic|aicc|chi2|redchi|…>. See Exports and column names. For weighted fits, chi2, redchi, AIC and BIC use the weighted residuals (residual/σ); for unweighted fits they assume unit variance. Either way, compare models only on the same data. Weighted fits also export gof_weighting (0 none, 1 Poisson, 2 relative Poisson), gof_residual_std_normalised, gof_chi2_reduced_weighted and gof_poisson_gain. A failed fit has empty columns and gof_success = 0 (see Failed fits).

Fit health

Weighting

XPS spectra are counts, and counting noise grows as √counts: ±100 at 10 000 counts but ±5 at 25. An unweighted fit treats a 50-count miss as equally bad everywhere, so the brightest points dominate. Poisson weighting divides every residual by its expected noise σ, as CasaXPS does by default (Cookbook p.119). Choose it at the top of the Peak Fitting step:

WeightingWhat it does
Auto (default)Poisson for XPS pipelines, unweighted for other techniques.
Poissonσ = √counts when the file holds raw integer counts (or counts/s with dwell time and scans). χ² then has an absolute meaning. When the “counts” are scaled, averaged or normalised (non-integer, typical of synchrotron data), it switches to relative Poisson.
Relative Poissonσ² = g·y: Poisson-shaped weights with an unknown gain g, which the fit estimates (gof_poisson_gain). The relative weights are right, but the reduced χ² and the normalised residual STD are ≈ 1 by construction, so they are not an absolute quality test.
NoneUnweighted least squares, as before.

σ always comes from the raw counts of the file, before any static background is subtracted. Crop, x-axis calibration, static baseline subtraction, normalisation (σ rescaled exactly) and cosmic-ray removal keep it. Smoothing, resampling, derivatives, reference transforms and averaging change the statistics: after them the fit runs unweighted and says so. Counting statistics are known for multi-block XPS files (VAMAS, NeXus, SPECS Prodigy); single text files are fitted unweighted.

Normalised residual STD (gof_residual_std_normalised) is the spread of residual/σ. For raw counts it should be about 1: well above 1 means a systematic misfit (missing component, wrong line shape or background); well below 1 means overfitting or data that are not raw counts. Tick Show normalised residual in the Peak Fitting step (or Normalised residual (/σ) in Analyze → Plots → Fit diagnostics) to draw residual/σ, where a good fit stays within about ±2 everywhere.

Weighting is on by default for all XPS fitting steps, including pipelines saved before it existed. Re-running an older XPS pipeline therefore gives slightly different parameters. Set None to reproduce an old unweighted fit exactly.

Failed fits

A fit that cannot run (invalid set-up, optimizer error, empty spectrum) is recorded, not hidden. The fitting step still passes the raw spectrum through, so later steps and plots keep working, but in an analysis run:

  • all of that fit's parameter and area columns are empty and gof_success = 0;
  • the run carries a warning and a fit_failures summary (counts plus the affected spectra and the reason). Analyze shows an amber ⚠ n fits badge in the run list and the details under Overview;
  • fit_health.csv in the fit-curve export lists the spectrum with fit_status = failed and the reason;
  • MCP get_analysis_runs_by_id and post_analysis_jobs_wait return the same warnings.

A fit that ran but did not converge (success = 0 from the optimizer) is flagged as not converged; its parameters are kept so you can inspect them. A fitting step whose window does not overlap the spectrum (for example an O 1s recipe meeting a C 1s spectrum in a multi-region pipeline) is not applicable: it is skipped silently and is not a failure. Restrict steps with the region selector to keep this explicit.

Every fit also reports gof_n_at_bound (free parameters sitting on a bound: the model is asking for more freedom than it has), gof_bg_gt_data_frac (fraction of points where the fitted background is above the data), gof_resid_mean_edge_lo / gof_resid_mean_edge_hi (mean residual over the outermost ~5% of the window at the low / high x end) and gof_resid_lag1_autocorr (≈0 for noise, close to 1 for a structured residual). The fit-diagnostics badge turns amber when a parameter is on a bound, the background is above the data in more than 10% of the points, or the residual autocorrelation exceeds 0.7. A background above the data at the window edge usually means the peaks are missing intensity (for example satellites that are too weak) and the background is compensating; fixing the background alone will not cure it. The fit-curve export zip also contains fit_health.csv.

Step numbers and column prefixes

The observation columns of a fitting step are prefixed s{N}_ where N is the 0-based position of the step in the pipeline (step_index). The step number used by the fit-curve and preview endpoints (fitting_step_num) is 1-based. GET /analysis/runs/{id}/fitting-steps lists both and the column_prefix; the endpoints also accept fitting_step_index instead of fitting_step_num.

Uncertainties

Every fit reports a 1σ error for each free or linked parameter, for every peak area and for %area (the peak's share of all peak areas in that fit; backgrounds and DS/GDS tails are not counted). The errors come from the fit covariance, scaled by the reduced χ² (lmfit default), so they grow when the model misfits. Linked parameters and areas get their error propagated through the link expression. Fixed parameters have no error. Analyze → Plots → Fit diagnostics lists each value as value ± error.

The covariance is a linear approximation. It underestimates the uncertainty when the background depends on the data (Shirley) or peaks overlap strongly. Monte Carlo (as in CasaXPS) measures that directly: the best fit is taken as the truth, noise is added n times (Poisson σ = √counts, relative Poisson σ² = g·y with the fitted gain, or constant σ = RMSE for unweighted fits), and every copy is refitted with the background recomputed. The spread of the refitted values is the uncertainty. In Fit diagnostics choose Replicates (default 100), Seed and the spectra, then Run Monte Carlo. The table shows the best fit ± covariance error, the Monte Carlo SD and 95 % interval, and their ratio; a ratio well above 1 marks uncertainty the covariance misses. Same seed, same result. API: POST /analysis/runs/{id}/monte-carlo-jobs, then GET /analysis/monte-carlo-jobs/{job_id}/summary (MCP: post_analysis_monte_carlo_jobs, get_analysis_monte_carlo_summary). Cost is spectra × replicates fits (server limit SERSFLOW_MC_MAX_FITS, default 20000).

Parameter sweep

POST /analysis/runs/{id}/sweep-jobs (MCP: post_analysis_sweep_jobs) fixes parameters of one fitting step on a grid (e.g. the shared FWHM) and refits the run's spectra at every grid point. The result zip has sweep_summary.csv (per grid point, sorted by mean RMSE, with the fit-health columns) and sweep_points.csv. Calibration and earlier steps are not recomputed.
